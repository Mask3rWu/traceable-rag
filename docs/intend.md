# 改动点备忘

本文件登记未来可能实施的各类改动点：每条只写**改动动机**与**改动方案（方向）**，不写已实现细节，不占变大段论证。改动落地后再移出或标记完成。

---

## 【混合检索架构】

**动机**

当前 Dense、BM25、原文分处三个物理存储：pgvector（向量）、磁盘 bm25s 索引（词法）、磁盘 chunks.jsonl（权威原文）。两者都只在检索时返回 `chunk_id + content_hash + score`，原文再由 ChunkCatalog 回读 chunks.jsonl；而 pgvector 表虽含 `text` 列却从不读出。导致：

- 文本权威源在多处漂移，一致性靠 content_hash 显式校验兜底（stale 即报错）；
- 小规模（3779 chunk / 47 篇）尚可，规模上来后"回读取文 + hash 兜底"成为负担。

**方案**

按规模梯度化处理，hash 从"兜底保险丝"升级为"跨存储的公共版本号"：

1. **不换引擎的中期**：把完整 chunk（含 text 与溯源字段）落成 PG 规范表，Dense、BM25 都按 `chunk_id` 从 PG 取原文，不再回读磁盘 chunks.jsonl；bm25s 与 pgvector 本体不动，中文分词仍在 Python 侧。进库与 bm25s 建索引由同一带版本号的"一篇章"编排，检索只认已发布版本。
2. **大规模才换引擎**：bm25s 单机磁盘不足时，词法升到 ES/OpenSearch（Lucene 原生 BM25+中文分词）或并入稀疏向量（SPLADE）与 Dense 同库做 hybrid；接 Cross-Encoder Rerank（现为 Noop）；摄入走异步队列 + 统一 revision 发布快照，一致性与分片交由引擎承载，反而删掉手工 hash 兜底。

**要点**：权威原文源必须单一（chunk 规范表）；磁盘 chunks.jsonl 保留为 PG 读 chunk 失败时的**只读降级读副本**，用 content_hash 校验两个副本一致、但不做双源一致治理（不整套同步/对账/版本仲裁）；保证正文与其页码/块/引用一起对齐的溯源能力是领域护城河，任何重构都不能丢。任何降级/兜底依赖的备选通道，故障域须与 PG/chunk 主通道正交（见【检索工具失败处理中间层】）。

## 【检索工具失败处理中间层】

**动机**

核心检索工具（search_knowledge）的真实 IO 只有 embed 与 pgvector 连接两处：embed 有 SDK `max_retries=3`，但 `PgVectorSearchStore` 的 DB 连接完全无重试。一旦瞬时抖动，异常被 `ToolNode(handle_tool_errors=True)` 捕获转成 error ToolMessage 回喂给 LLM；LLM 既无退避能力也无"等待恢复"语义，只会反复重发检索、烧步骤预算，最终才 failed——把 LLM 根本解决不了的基础设施错误错位交给了它。

**方案**

在 agent 工具与底层 IO 之间加一层指数退避重试，只把可恢复抖动挡在 agent 之外：

1. 按错误性质分流：瞬时基础设施异常（DB `OperationalError`、连接/超时、embedding 5xx）→ 指数退避重试（attempts≈3、`0.5s*2^n`+抖动、上限 ~4s）；应用层错误（未知证据 ID 的 ValueError、cancelled 的 RuntimeError、参数校验）→ 不重试，原样上抛；软信号（`budget_reached` 返回）根本不是异常，不碰。
2. 放置两层：低层在检索服务（dense/通用 `retry.py`，补上 DB 与 embedding 对称的重试）；工具中间层做薄封装，把 embed+DB 瞬时错误统一成"可重试集合"。
3. `ToolNode(handle_tool_errors=True)` 保留作最后兜底，专门承接不可重试的逻辑错误，继续让 LLM 修正。
4. 分级不止"重试/不重试"：dense（embed+DB）故障而 BM25 本地索引完好时，**降级纯 BM25 继续研究**并打 `degraded` 标记供下游知晓；不满足降级条件才升级为彻底失败，转向【彻底失败兜底】。

**要点**：重试只包住底层 IO 调用、绝不包整个工具函数（否则会重试取消/未知 ID 这类语义错误）；分工是"退避解决能自愈的抖动、LLM 只解决它真能修正的逻辑错误"。降级通道有效的前提是**故障域与主通道正交**（本地 bm25s 索引、本地原文快照），而"统一上云、单一权威源"的演进会侵蚀这一前提，是此消彼长的 trade-off，须作为红线保留（见【混合检索架构】）。

## 【彻底失败兜底】

**动机**

检索、模型等核心基础设施在"退避重试 + 降级后仍失败 / 判定永久（auth 401、配置错、模型下线）"时，当前失败路径处置不足：checkpoint 只在章节波次完成后落盘，失败路径不主动保存，章节中部进度会丢；失败原因只写进一次性 packet 的 diagnostics，无结构化持久化，运维无法判断该补发还是修配置。此兜底通用——检索与模型不可用同样适用，故独立成条，不只挂在检索工具下。

**方案**

判定永久后做"终止 + 干净失败"，而非放任它烧预算：

1. 终止时**主动落盘一次 checkpoint**，保留已达成章节；基础设施恢复后 `resume(run_id, start_chapter=...)` 续跑（恢复机制已具备，`attempt` 计次防无限重启）。
2. **持久化不可用原因**：结构化写入（run 的 error/diagnostic + metrics），写明是哪个通道、哪类异常、退避尝试几次、是否已降级，支撑运维判别该补发还是修配置。
3. 区分 `cancelled` 与永久不可用：取消是主动行为，不触发重试/重启；永久不可用才走终止路径。

**要点**：彻底失败要"干净"——留好 checkpoint、留清原因、留出恢复入口；既得能补发，又得能判断该不该补发。终止动作本身若依赖已故障的通道（如把原因写进同样挂掉的 PG），须有独立落盘通道。

## 【图表内容检索】图片 / 表格 / 公式内容级可检索

**动机**

核心需求是让图片、表格、公式的**内容本尊**被检索到，而非靠文字旁注。当前三对象可达性参差，且有一个真实死字段：

- `visual_text`（MLLM 描述）是**死字段**：`_embedding_text` 只拼文档名+章节+正文（不含 visual_text），BM25 明确只索引 `source_file+document_id+heading_path+text`——两个主力通道都不读它，写了等于没写。
- 表格**格子内容完全不入索引**：SLANeXt 结构化结果没建可检索文本，表格只余 MLLM 描述（而它在死字段里）。
- 图片**像素完全不入索引**：唯一载体是死字段描述。
- 公式 LaTeX 已在 `text`，BM25/Dense 都索引 `text` → **符号/编号级已经可检索**，只缺语义级。

**方案**

原则是"**内容放对通道**"，而非"写进可能没人读的描述字段"；多通道 + RRF 融合（Dense + BM25 已存在）承接新通道，零架构突变。三类各选一条主通道：

1. **图片（图表为主）**＝描述文本向量为主，像素向量为补充。图表检索诉求多在"图讲什么+图内数字/名称"，恰是 MLLM 转文字再进 dense 的强项；image embedding（SigLIP 系，~1G，本地可跑）对坐标轴小字、格子数字识别弱，仅"以图搜图/未概括像素"时才值得，先不默认要 B。**首选动作是救活死字段**：让 `visual_text` 真正进 dense embedding（或独立低权向量）并让 BM25 也索引它，用现成 eval 量化"描述进向量前后 hit_rate/evidence_recall 差多少"，再决定要不要上 image embedding。
2. **表格**＝结构化单元格索引为主 + 检索后 LLM 按需读格。SLANeXt 行列拼成 `表题+表头+单元格` 文本建独立 BM25 通道，让"某装备重量 52t""毁伤等级 B 对应 X"这类**格子值**可精确召回；检索到表后由 LLM 读格取精确值。表格的 image embedding 版式相似基本可省。
3. **公式**＝符号/编号级保持现状（已在 text），语义级补独立低权通道。查编号/符号回溯证据已够；用户若按概念直问（"超压随距离怎么衰减"）才补一句 MLLM 语义并入低权索引。不上重型数学语义专用检索。

**要点**

- 三类内容**不走同一条正文 embedding 向量**：图片/表格/公式各开独立通道或独立低权向量参与 RRF，既让内容可检索，又天然隔离——这正是"防稀释"的朴素解法，不是需要专门恐慌的风险。
- 任何"防稀释/通道收益"都用现有 eval 基线（3779 chunk、2083 题，evidence_recall/hit_rate/MRR）量化，不靠主观权衡拍板。
- 最优先且无次生成本的一步是**救活 `visual_text`**：最小改动、立刻让图片/表格多一层可检索；评估后失败再谈是否引入 image embedding 新模型。
- 数据边界不变：新通道返回值仍是 `chunk_id + content_hash + score`，正文照旧经 ChunkCatalog 从 chunks.jsonl 回读；`doc.json` 仍是唯一事实源，视觉/语义产物只作检索辅助。内容通道的成功与否反过来指导解析层该不该补公式 LaTeX 二次校验——这触发【混合检索架构】的权威源讨论，属此消彼长的 trade-off。

## 【检索评测偏置与 RRF 调参前提】

**动机**

2026-09-05 对 `eval/rag/v2` 全 2083 题逐题诊断（`scripts/diag_gold_ranks.py`，逐题查 dense/bm25 对证据块的各自 rank）显示，v2 上 MRR 的差距是**排序**而非**召回**造成的，且该排序信号被词法偏置污染：

- 93.5% 的题（1948）两路都在 top-50 找到证据块；dense 对证据块 best rank 中位 1、**均值 3.5**，bm25 均值 2.0，**27.3% 的题 dense 排得比 bm25 更靠后**。dense 的"差"主体是"找到了但位次靠后"，不是漏检索（Recall@50≈95%）。
- 位次差的来源是**度量偏袒**而非 bm25 更强：bm25 的 `lexical_text` 索引了 `source_file`+`document_id`，而 v2 题目是 section_exact/document_exact、大量逐字引用原文/文档名，bm25 靠名字+词元重合把证据块顶到 #1；69 道 dense 完全漏掉的题多为这类 "文档名/逐字引用" 题及公式符号题（SRPN、qinc、R）。
- **反证**：武双章英文论文的 ~20 道英文题几乎全为 dense_only——中文 jieba 对英文查询无词法下嘴处、bm25 瘫痪，dense（bge-m3 跨语言）独自救回。说明 dense 的真实能力在"无词法重合"处，而当前 MRR/RRF 指标几乎不记它。
- 另有 both_miss 33 + unreachable 5：两路都够不着；5 个 unreachable 即 result.md 记的 4 个缺失 chunk 块；table_formula 为最割裂题型（9 both_miss，6 bm25_only）。

**方案**

不在这套带偏置的信号上调 RRF 权重；应先修度量偏置、再取权重决策：

1. **评测侧中和 id 偏置**：bm25 的 `lexical_text` 去掉或不索引 `source_file`+`document_id`，或至少并存一版"无 id 指标"再比——否则 bm25 白得文档名直查优势。
2. **权重决策延后到通道改造之后**：【图表内容检索】（救活 visual_text、表格格子内容）与【混合检索架构】（权威源收敛）都会改 Dense embedding 输入与 BM25 索引内容，当前基线随之全变；故此条排在它们之后，不提前调参。
3. **both_miss（33）归因**：按"标注问题 / 切块缺失 / 真难题"归因，据此决定是修订标注还是新建更均衡的 v3 题（呼应 result.md 改进方向）。
4. **公式/表格符号语义**为两路共同洞，归【图表内容检索】公式语义级通道处理。

**要点**：本次诊断用 v2 + 现有索引跑出，结果只对"当前内容基线"成立；诊断工具与明细可复用（留存 `eval/rag/diag_gold_ranks.tsv`、`scripts/diag_gold_ranks.py`），作后续改通道后重诊的对照尺。该条目依赖并排在【图表内容检索】【混合检索架构】之后。

## 【证据池卫生：预览即弃、以引用为准】

**动机**

`run.evidence` 是整条 run 共享的检索登记池（`EvidenceWorkspace._evidence`，`tools.py`；写入 `graph.py:1023/1506/1624`），它**不经任何正常路径进模型上下文**——模型上下文里只有检索时的 snippet 预览（quote≤600，`tools.py:133`）与模型点名 read 的全文（`tools.py:148`）。它的消费方只有两处：**续跑恢复源**（`graph.py:1545` restore 整池）与 **`evidence_count` 指标**（`api/manager.py:165/297/313`）。它**不是答案的证据**。

对宽综合题实测，池里 **60~85% 是"搜到但从未引用"的死重**（池 384→引用 80、池 190→引用 76 等）。伤在：

- 落盘冗余：每块存 quote，几百块 ≈ 半 MB/run 纯磁盘写入；
- `evidence_count` 失真：显示几百，实际靠几十，运维读数是骗人的；
- 续跑 restore 连带填回死引用与噪音；
- 作为评测相关集**不可用**——这正是【检索评测偏置与 RRF 调参前提】里"证据集过大"灌水问题的元凶。

**方案**

采用"以引用为准"原则：**预览即弃、引用才留**。

1. 检索工具只在**模型真正 read（取全文）或被答案引用**时，才允许该 chunk 进池、才落盘；只看了 snippet 的用完即弃。层上不设全局池上限为首选，避免截掉宽题真需内容。
2. 同一判断点（read/引用）合并"检索工具上下文卫生"：先给预选→模型选→只留模型保留的块，移出未选块——与【证据池剪枝】是一个改动，不是两个。
3. 保留续跑所需的最小记忆；不必把整池死引用写进 checkpoint。
4. 前置保障：引用字段需保证记全（已发现 3 个 fast-mode run 的 `answer.evidence_ids` 为空，见【检索评测偏置与 RRF 调参前提】内盘点线索），否则"按引用剪枝/按引用评测"无从谈起。

**要点**：该改动后 `run.evidence` 从"几百块的检索池"变为"几十块的引用集"，正好可作为评测的 citation 相关集，与【检索评测偏置与 RRF 调参前提】同一条逻辑链、优先级并列。
